# ADR 0014: Kubernetes manifests for local `kind` deployment

## Status
Accepted

## Context
The plan places Kubernetes (Fase 5) *after* auth-service (Fase 4), specifically to
avoid rewriting manifests twice once a fifth service and JWT verification exist. The
user explicitly chose to jump ahead ("vamos em frente") after asking whether the
cluster would run locally — it does, via `kind` (Kubernetes-in-Docker), not a managed
cloud cluster. This is a deliberate, accepted deviation from the plan's own stated
sequencing rationale: these manifests are a first pass and will need a second one once
auth-service exists (new Deployment, JWKS-aware readiness checks, Secret for the
signing key).

`kubectl` (v1.36.1) was already installed with Kustomize v5.8.1 bundled, so
`kubectl apply -k` works without a separate `kustomize` binary. `kind` was not
installed (`brew install kind` added v0.32.0); `minikube` was not needed.

## Decision
- **`kind` over `minikube`**: no VM layer, runs the whole control plane + node as
  Docker containers, which is the lowest-friction way to get a real cluster locally
  and matches how the images themselves are already built (via plain `docker build`,
  no `minikube docker-env` step).
- **Kustomize (`kubernetes/base/`), not raw manifests or Helm**: the manifests are
  static and single-environment for now (no dev/staging/prod overlays yet), so a
  `kustomization.yaml` tying resources together plus a `secretGenerator` is enough
  structure without introducing Helm's templating for a single environment.
- **StatefulSet + `volumeClaimTemplates` for `postgres` and `ollama`** (headless
  `Service`, `clusterIP: None`), **Deployment + Service for the four stateless
  services** — mirrors the plan's own 5a description exactly.
- **initContainer wait-loops replace docker-compose's `depends_on: condition:
  service_healthy`**: Kubernetes has no native cross-Deployment "wait until that other
  Deployment is healthy" primitive. Each Java service's Pod spec gets a `busybox`
  initContainer polling `nc -z <host> <port>` for Postgres/Ollama, and — for
  rag-service (waiting on ingestion-service) and chat-service (waiting on rag-service)
  — `wget -qO-` against the upstream's `/actuator/health` and grepping for `"UP"`,
  preserving the exact same startup ordering the plan's `depends_on` chain enforces in
  `docker-compose.yml`.
- **Secrets via Kustomize's `secretGenerator`, never committed**: `kubernetes/base/
  .env.secret` (gitignored) holds `DB_USER`/`DB_PASSWORD`; only a placeholder
  `.env.secret.example` is committed. Base64 in a committed Secret YAML is not
  encryption, so it was never on the table as an option here.
- **Same fix applied to `docker-compose.yml` in the same pass**: the plan's own
  pending gap ("credenciais hardcoded") and this ADR's Secret work are the same
  problem in two places — `docker-compose.yml` now reads `${DB_NAME:-ragplatform}` /
  `${DB_USER:-ragplatform}` / `${DB_PASSWORD:-ragplatform}` from an optional,
  gitignored root `.env` (falling back to the previous hardcoded values so the
  existing local workflow needs no changes), with `.env.example` committed as the
  template.
- **Ingress is secondary, `kubectl port-forward` is primary**: `kind` does not bundle
  an ingress controller by default, so `kubernetes/base/ingress.yaml` (host
  `rag-platform.local`, `ingressClassName: nginx`) only works after separately
  installing `ingress-nginx`. The plan's own "pronto quando" criterion
  (`kubectl port-forward` to `web-ui` working end to end) is the primary, always-
  available verification path, documented as such in `kubernetes/README.md`.
- **Image tags `rag-platform/<service>:latest`, `imagePullPolicy: IfNotPresent`**:
  built locally via plain `docker build`, then `kind load docker-image` — no registry
  involved, consistent with a local-only demo cluster.

## Consequences

- **Kustomize renders cleanly and dry-run validated**: `kubectl kustomize
  kubernetes/base` produces valid manifests for all 9 resource files before any
  cluster interaction was attempted.
- **Verified for real** (not just `kubectl apply` succeeding): built all 4 images,
  created a `kind` cluster, loaded the images, applied the kustomization, watched pods
  reach `Running`/`Ready` in the expected dependency order (postgres/ollama first, then
  ingestion-service, then rag-service, then chat-service, web-ui independently), then
  reached the platform via `kubectl port-forward svc/web-ui` (HTTP 200) and via
  `kubectl port-forward svc/rag-service` — uploaded a real document through
  ingestion-service, asked a real question, and got back a correct, cited answer
  (`"O padrão de saga coordena uma sequência de transações locais entre serviços..."`)
  generated by the real `llama3.1` running inside the cluster's own `ollama-0` pod.
- **First-boot latency is real and worth documenting**: each Java service pulls its
  own Ollama model(s) on startup (`pull-model-strategy: when_missing`) against a
  freshly created, empty `ollama-0` volume — unlike docker-compose's `ollama-data`
  volume, which had already-pulled models from earlier phases. The first
  `kubectl apply` in a brand-new cluster pays the full model-download cost inside the
  readiness-probe window, not just container startup.
- **Real bug found and fixed**: on the first live run, `rag-service` restarted once
  (`Exit Code: 143`) — its `livenessProbe` (`initialDelaySeconds: 40`) fired before the
  first-boot `llama3.1` pull finished, killing the container mid-pull. Fixed by adding
  a `startupProbe` (`failureThreshold: 30`, `periodSeconds: 10` — up to 300s) to all
  three Java services' manifests; `startupProbe` suspends liveness/readiness checks
  until it passes once, so a slow first boot no longer looks like a hung container.
  Re-tested from a fully clean `kind delete cluster` + recreate: zero restarts across
  all 6 pods.
- **Real bug found, not a manifest problem**: `ollama-0` itself was `OOMKilled` (exit
  143→137) during the very first real `/api/v1/ask` call. Root cause wasn't the pod's
  own `8Gi` memory limit — it was that the entire Docker Desktop VM hosting the `kind`
  node only has **7.75GiB total** (`docker info --format '{{.MemTotal}}'`), and the
  `docker-compose` stack from earlier phases was still running *at the same time*,
  competing for that same shared pool. A per-container `resources.limits.memory` is
  meaningless once the host itself runs out of real memory — the kernel OOM-kills
  whatever process is using the most, regardless of that container's own configured
  limit. Fixed operationally, not by shrinking the limit: `docker compose down` before
  bringing up `kind` frees the memory `kind`+`ollama` actually need. This cascaded into
  a second, *correct* behavior worth noting rather than fixing: Resilience4j's `ollama`
  circuit breaker (ADR 0009) tripped OPEN after the OOM-caused failure and rejected the
  next call immediately (`"CircuitBreaker 'ollama' is OPEN"`) rather than retrying
  against a service known to be unhealthy — exactly its job. It self-recovered to
  half-open after `wait-duration-in-open-state: 30s` and the next real request
  succeeded with a correct, cited answer. Documented in `kubernetes/README.md` as a
  prerequisite: don't run `docker-compose` and the `kind` cluster at the same time on a
  memory-constrained host.
- **Known, accepted rework ahead**: adding `auth-service` (Fase 4, still pending) will
  require a fifth Deployment+Service here, a Secret for its JWT signing key, and
  updating the other three services' initContainer/readiness assumptions — exactly the
  double-work the plan's original ordering was designed to avoid. Accepted trade-off
  per explicit user direction, not an oversight.
- **No TLS, no autoscaling, no PodDisruptionBudget**: out of scope for a local demo
  cluster; TLS is deferred to the public deploy phase (Fase 7b).

## Update: the `auth-service` second pass (`docs/ROADMAP.md` Tier 1 #1)

The rework predicted above landed: `kubernetes/base/auth-service.yaml` adds its
Service+Deployment, `configmap.yaml` gained `AUTH_SERVICE_BASE_URL`, and
`ingestion-service.yaml`/`rag-service.yaml`/`chat-service.yaml` each gained a
`wait-for-auth-service` initContainer (`wget` against `/actuator/health`, same idiom
already used for rag-service→ingestion-service and chat-service→rag-service) —
mirroring `docker-compose.yml`'s `depends_on: auth-service: condition: service_healthy`
on all three exactly. `auth-service` itself only waits on Postgres (`nc -z postgres
5432`) since it never calls Ollama, and skips the `startupProbe` the other three carry
for that reason — there's no slow first-boot model pull to protect against here.

**No JWT signing-key Secret was added** — unlike what this ADR originally predicted,
`auth-service` still generates its RSA keypair in memory on every restart (ADR 0016);
that only becomes relevant once Security Phase 4 (persistent JWT key,
`docs/SECURITY-HARDENING-ROADMAP.md`) actually exists. Adding a Secret for a key the
service doesn't yet know how to load would be speculative.

**Verified for real, not just `kubectl kustomize` rendering cleanly** (which was also
checked first): built all 5 images, `docker compose down` first (this host's Docker VM
is the same memory-constrained one from the original verification — running both at
once already caused a real OOM once, no reason to risk it again), created a fresh
`kind` cluster, loaded the images, applied the kustomization, and watched all 7 pods
(`auth-service`, `ingestion-service`, `rag-service`, `chat-service`, `web-ui`,
`postgres-0`, `ollama-0`) reach `Running`/`1/1 Ready` with **zero restarts** — including
`auth-service`, whose init ordering had never been exercised in a cluster before.
Then, through `kubectl port-forward` to `auth-service`/`ingestion-service`/
`rag-service` individually: registered a real account (real `201`, a genuine RS256 JWT
back), uploaded a real Markdown document through `ingestion-service` (first attempt
correctly rejected as `415` for a bare `application/octet-stream` content type — ADR
0022's magic-byte validation working inside the cluster exactly as it does locally —
second attempt with the right content type succeeded, `201`), and asked a real question
against `rag-service`, getting back a correct, cited answer generated by the actual
`llama3.1` running in the cluster's own `ollama-0` pod, routed correctly as `"answer"`
(not `"diagram"` — ADR 0024's classification call also exercised for the first time in
a cluster). Cluster torn down afterward (`kind delete cluster`); the local
`docker-compose` stack that was stopped for this test was restarted immediately after.
